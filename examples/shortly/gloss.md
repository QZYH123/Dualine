# shortly 是怎么工作的

一个短链接服务。这份对照笔记按一次请求的路径来读它：从进程启动，到一条网址被缩短、存下、再被访问。右侧的代码会跟着你读到的段落走。

## 它做什么

shortly 只做一件事：把一个长网址换成一个七位的短码，之后有人访问短码，就把他送回原来的网址。整个服务是[三个 HTTP 接口](src/server.ts#L18-L59)：`POST /api/shorten` 负责缩短，`GET /:slug` 负责跳转，另有一个[统计接口](src/server.ts#L32-L44)回报点击次数。

代码分成五个文件，职责很清楚：`server.ts` 收请求，`validate.ts` 检查网址，`slug.ts` 生成短码，`store.ts` 读写 SQLite，`index.ts` 把它们装配起来。下面按一次请求经过的顺序逐个读。

## 启动

进程从 `index.ts` 开始。它先读三个环境变量——[端口、数据库路径、对外的基础地址](src/index.ts#L4-L6)——每一个都有默认值，所以本地直接运行不需要任何配置。

然后是两步装配：[先打开存储，再把存储交给服务器](src/index.ts#L8-L9)。`createServer` 不自己创建数据库，而是从参数接收一个 `Store`。这样测试时可以塞进一个内存实现，服务器代码一行都不用改。

最后是[监听端口](src/index.ts#L11-L13)，以及一段容易被忽略的[退出逻辑](src/index.ts#L15-L23)：收到 `SIGINT` 或 `SIGTERM` 时，先停止接收新连接，再关闭数据库，最后退出。顺序反过来，就可能在写入中途切断文件。

## 一次缩短请求

`createServer` 里先做两件小事：[关掉 `x-powered-by` 响应头](src/server.ts#L15)，不向外暴露框架；再[把 JSON 请求体限制在 4KB](src/server.ts#L16)——一个网址不需要更多，这也顺手挡掉了超大请求。

缩短接口的主体只有[三行](src/server.ts#L20-L22)：把请求体里的 `url` 交给 `normalizeUrl` 清洗，用 `insertWithRetry` 拿到一个短码，然后回一个 `201 Created`。任何一步抛出的错误都被 `catch` 住并[交给 `next`](src/server.ts#L27-L29)，由统一的错误处理器决定状态码。

`insertWithRetry` 的名字已经说明了它做什么。生成随机短码后尝试写入；[如果写入失败，说明这个短码已被占用，就再生成一个](src/server.ts#L65-L73)。最多试五次——七位 base62 有三万五千亿种组合，连续五次撞车在实践中不会发生。这个上限只是让「不可能」有一个明确的出口，而不是死循环。

统一的[错误处理器](src/server.ts#L75-L87)只区分两类：`ValidationError` 是用户的问题，回 400 并原样返回说明；其他一切都是服务器的问题，记日志、回 500，不泄露细节。

## 短码从哪里来

短码由 `slug.ts` 生成。字符表是[数字加大小写字母，共六十二个](src/slug.ts#L3-L4)，长度[固定七位](src/slug.ts#L6)。62 的 7 次方约等于 3.5 万亿，对个人项目来说等于用不完。

随机源是 `node:crypto` 的 [`randomBytes`](src/slug.ts#L1)，而不是 `Math.random`。后者是可预测的伪随机；短链接虽不是密码，但可被猜出的短码，意味着别人能枚举出你存过的所有网址。

这里有一处细节值得停一下。一个字节有 256 种取值，62 除不尽 256，如果直接对 62 取模，前八个字符会比其他字符略多出现一些。代码的做法是[丢弃大于等于 248 的字节](src/slug.ts#L8-L10)，只在 0 到 247 这个恰好是 62 倍数的区间里取模，这样[每个字符出现的概率才真正相等](src/slug.ts#L16-L19)。这叫拒绝采样，代价是大约 3% 的字节被扔掉，所以每轮多取一倍的字节来减少循环次数。

另有一个[合法性检查](src/slug.ts#L25-L29)供跳转接口使用：只接受 4 到 16 位的字母数字。它并不判断短码是否存在，只是在查数据库之前，先把明显不对的路径挡在门外。

## 存下来

存储层用的是 SQLite，通过 `better-sqlite3` 访问。整个模式只有[一张表](src/store.ts#L19-L26)：短码是主键，网址非空，加上创建时间和点击数。主键约束本身就是防重复的机制——不需要先查再插。

`openStore` 在[打开数据库之前先确保目录存在](src/store.ts#L29)，然后[开启 WAL 模式](src/store.ts#L32)。WAL 让读和写可以同时进行，对于「大量跳转读、偶尔缩短写」的访问模式正合适。

三条 SQL 在启动时[预编译一次](src/store.ts#L35-L43)，之后每个请求只是绑定参数执行，不再重新解析。`better-sqlite3` 的 API 是同步的，这在 Node 里看着反常，但 SQLite 本地文件的读写只有微秒级，同步反而比事件循环切换更快。

[`insert` 返回布尔值而不是抛异常](src/store.ts#L46-L54)：撞上主键冲突时返回 `false`，其他错误照常抛出。这个选择让上层的重试逻辑可以写成一个简单的 `if`。判断冲突靠的是 [SQLite 的错误码](src/store.ts#L70-L76)，而不是去匹配错误信息的文本。

## 跳转

访问 `/:slug` 时，服务器[先做形式检查](src/server.ts#L47-L51)，再[查库](src/server.ts#L52-L56)。两处都回 404，且都是纯文本——这是给浏览器看的页面，不是给程序看的 API。

找到之后，[记一次点击，然后以 302 跳转](src/server.ts#L57-L58)。这里选 302 而不是 301 是有意的：301 会被浏览器永久缓存，之后的访问不再经过服务器，点击数就不准了；302 每次都回来，统计才有意义，将来要改目标网址也还改得动。

路由顺序也有讲究：`/:slug` 会匹配任何单段路径，所以它必须[注册在 `/api/...` 之后](src/server.ts#L46)，否则 `api` 本身会被当成一个短码去查。

## 检查网址

`normalizeUrl` 是缩短接口的第一道门。它依次拒绝[空值和非字符串](src/validate.ts#L14-L16)、[过长的输入](src/validate.ts#L17-L19)，然后用[浏览器同款的 `URL` 解析器](src/validate.ts#L21-L26)判断格式。凡是拒绝，都抛出 `ValidationError`，携带一句能直接展示给用户的说明。

格式正确还不够。只允许 [`http:` 和 `https:`](src/validate.ts#L28-L30)，挡掉 `javascript:` 和 `file:` 这类协议；再拒绝 [`localhost` 和内网地址](src/validate.ts#L31-L33)，因为一个公开的跳转服务如果允许指向内网，就会成为探测内网的跳板。

最后[抹掉 `#` 之后的片段](src/validate.ts#L35-L36)并返回规范化后的字符串——`URL` 会顺手补上末尾的斜杠、把主机名转成小写，这样同一个网址的不同写法在库里只占一条。

## 还没做的事

读到这里，你已经看完了全部代码。有几件事它没有做。知道边界在哪里，比假装完整更有用。

没有鉴权，任何人都可以创建短链；没有限流，[缩短接口](src/server.ts#L18)可以被无限调用。要加，最自然的位置是 `app.post` 之前的一个中间件。

没有过期时间，也没有自定义短码。前者需要在[表结构](src/store.ts#L19-L26)里加一列 `expires_at`，并在跳转时检查；后者只需让缩短接口接受一个可选的 `slug` 字段，先过 [`isValidSlug`](src/slug.ts#L27-L29)，再走同一条 `insert` 路径——主键冲突的处理已经在那里等着了。
